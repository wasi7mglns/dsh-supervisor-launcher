# 修正：壳如何触发更新（对执行方案 §1 的更正）

> 起因：用户质疑——「壳是如何触发到更新？壳是通过内核来进行更新还是怎么样？
> 逻辑上，壳启动那一瞬间发现壳有更新时，应该**先更新壳**，然后再走引导；
> 引导顺序应是「先检测环境 → 检测壳 → 检测内核 → 进入主系统」。}」

---

## 一、先承认：上一版设计有真实缺陷

上一版把**内核**设为「更新权威 + 产物提供方」，同时又要求壳**在内核之前**更新自己。这两条**互相矛盾**：

```
冷启动 / 内核未安装 / 内核已损坏
   → 内核没起来 → /shell/update/v1/check 无人应答
   → 壳拿不到更新 → 只能「下次启动生效」
```

结果是：**用户永远不会在最需要的那一刻拿到壳更新**（即壳有问题、内核也起不来的时候）。
我把「谁提供产物」和「谁保证安全」这两件不同的事混成了一个角色。用户指出的正是这一点。

---

## 二、修正：把两个角色拆开

| 角色 | 承担者 | 说明 |
|---|---|---|
| **更新源**（版本元数据 + 产物） | **公网发布通道**（GitHub Release / CDN） | 壳**直连**，不依赖本机任何组件 |
| **安全网**（确认 / 回退 / 审计） | **内核（守卫）** | 唯一受监督的组件，负责壳失败时把它救回来 |

**一句话**：**壳直连公网自更新；内核不做更新源，只做安全网。**

### 为什么这样是对的

1. **冷启动自洽**：壳更新不再依赖内核是否在跑 → 满足用户要求「启动即更新壳」。
2. **与壳现有行为一致**：壳**本来就在直连公网**（`nodejs.org`、npm 镜像源），
   已验证其具备 HTTPS 能力（`ureq + tls`）。连发布通道不是新增能力。
3. **职责仍然最小**：壳只调用 Tauri 官方 updater 插件（成熟的平台安装机制 + 强制验签），
   不自造下载/校验逻辑。
4. **安全网仍然有效**：稳态下内核是 systemd 常驻服务（`Restart=always`），
   壳被更新坏掉时它**几乎总在运行**，能回退。

---

## 三、机制澄清：壳**无法替换自己正在运行的二进制**

这一点必须讲清楚，否则「壳先更新壳」会被误解为「进程内部原地改自己」。

**实际流程是「旧的装，新的跑，旧的退」**：

```
旧壳进程 (V_old) 启动
  ├─ 查发布通道：有 V_new？
  ├─ 无 → 直接进入门 1（环境）
  └─ 有 → ① 备份当前产物（回滚素材，关键）
           ② 下载 V_new + 验签（Tauri 强制）
           ③ 交给平台安装机制：
                Linux  AppImage ：替换 AppImage 文件
                macOS  .app     ：替换 .app 目录
                Windows NSIS    ：运行 -setup.exe（静默 passive）
           ④ app.restart() → 拉起 V_new 进程
           ⑤ V_old 退出
```

所以「壳更新壳」= **旧版本执行安装，然后重启进新版本**，而不是自我改写。

---

## 四、必须补上的一环：**回滚素材**

已核实 Tauri updater 是**原地安装（in-place）**——它把旧的替换掉，**不保留旧版本**。
因此：

> **若不主动备份当前产物，一旦新版本起不来，磁盘上就没有「能回去的版本」了。**

这直接决定两件事：

| 场景 | 备份由谁做 |
|---|---|
| 内核在运行（稳态） | **内核预取并保留上一版本产物** → 回退时重新应用（内核有网络 + 缓存 + 审计） |
| 内核未运行（首启 / 内核坏） | **壳自行备份**当前产物（Linux AppImage 只是文件，可行；macOS/Windows 较难）→ 壳自身回退 |

**诚实说明边界**：**首次安装时（内核尚不存在）没有自动回滚能力**。
因为那时既没有内核、也没有「上一个可用版本」。
→ 这对产品的要求是：**首次安装包本身必须是最保守、最稳的版本**，且安装器（.deb/.dmg/.msi）必须可靠。

---

## 五、修正后的引导顺序

用户提议：**环境 → 壳 → 内核 → 主系统**。方向正确，我做一处精化并说明理由。

### 最终顺序

```
壳进程启动
 │
 ├─[探针] 只读环境探测（~200ms，失败不阻断）
 │        平台 / arch / 网络可达性 / 安装形态(appimage|deb|nsis|app)
 │        目的：判断「能否自更新」，避免无谓等待
 │
 ├─[门 0] 壳自更新（直连公网发布通道）   ← 用户要求的「先更新壳」
 │        无更新 / 离线 / 不可自更新(deb) / 已达阈值 → **放行**
 │        有更新 → 备份 → 下载 → 验签 → 安装 → 重启进 V_new
 │
 ├─[门 1] 环境就绪：Node 运行时（低于最低标准才安装）
 ├─[门 2] 内核：检测 → 按**兼容区间**选版 → 安装
 ├─[门 3] 守卫就绪 → 面板
 └─[确认] finish_boot → 上报健康（= 更新确认信号）
```

### 为什么壳更新要排在 **Node 之前**（而非仅在内核之前）

| 理由 | 说明 |
|---|---|
| 壳是原生二进制，**不需要 Node 就能更新自己** | 更新壳无前置依赖 |
| **新壳可能带有不同的 Node 要求** | 例如新的最低版本、新的镜像/校验逻辑（`node.rs` 在壳里） |
| 用旧壳装 Node 有装错的风险 | 装完再被新壳判定不合规，等于白装一次（浪费带宽与时间） |

**所以**：廉价的**只读探针**可以放最前（符合你说的「先检测环境」），
但**会改动系统的壳更新**必须排在**Node 安装**之前。

用户原话「先检测环境 → 检测壳 → 检测内核」在**检测**层面完全成立；
我的精化只在于：把「**安装/更新**」类动作重新排序为 **壳 → Node → 内核**，
因为每个写动作都应该由**最新版本的壳**来执行，否则它可能执行的是旧规则。

## 六、内核作为安全网的完整职责（不含「提供产物」）

| 职责 | 说明 |
|---|---|
| **预取**（优化） | 周期性检查壳新版本并**提前下载缓存**，使壳的门 0 几乎瞬时（不依赖它也能更新，只是更快） |
| **备份** | 保留当前 + 上一个壳产物作为回滚素材 |
| **健康观察** | 读 `~/.dsh/shell/identity.json`（含 `attempt` 自增、`phase`、`version`） |
| **有界回退** | 更新未确认 + `attempts > 2` → 判坏版本 → 回退 + 加黑名单 + 事件 + 桌面通知 |
| **可观测** | `update-journal.json` + 事件日志 + 面板展示壳版本/更新状态/回退记录 |
| **版本配对** | 校验「壳 ↔ 内核」兼容区间（P6） |

**不再承担**：版本元数据的权威来源、产物的唯一分发方。

---

## 七、已核实的一个技术坑（多端点回退）

Tauri 官方文档原文：

> Tauri will **only continue to the next url if a non-2XX status code is returned**!

**含义**：`endpoints` 数组的**网络超时/连接失败不会触发回退到下一个端点**（那不是 2XX/非 2XX 语义）。

**对策**：
- 主要依赖**单一主端点**（公网发布通道），并对「检查」加**自己的短超时**（如 3s）。
- 「离线 → 放行」的控制权必须在**壳自己手里**，不能指望 updater 的多端点回退。
- 若确实需要多镜像回退，须在壳内做「先探测可用端点，再把可用端点交给 updater」。

## 八、对执行方案的具体修改

| 章节 | 原内容 | 修正后 |
|---|---|---|
| §1 目标架构 | 内核 = 更新权威 + 对内提供 `/shell/update/v1/*` | **壳直连公网发布通道**；内核 = **安全网**（预取/备份/观察/回退/审计） |
| §2.4 内核端点 | `GET /shell/update/v1/check`（作更新源） | 改为**仅内部管理端点**：`GET /shell/status`、`POST /shell/health`、`POST /shell/rollback`（不再是壳的更新源） |
| §2.5 Tauri 配置 | `endpoints=[本机内核]` + `dangerousInsecureTransportProtocol` | `endpoints=[公网发布通道]`，**HTTPS 原生满足**，**不再需要** insecure transport 开关（少一个安全妥协） |
| §3 P1 | 内核「发现→下载→验签→缓存→**对内提供**」 | 内核「发现→下载→验签→缓存（**供自己回退用**）」；**不提供**给壳 |
| §3 P2 | 门 0 端点 = 本机内核 | 门 0 端点 = **公网发布通道**；新增「**更新前备份当前产物**」 |
| §4 风险 K3 | 回环 HTTP vs TLS 强制 | **风险消失**（改公网 HTTPS 后不再需要该开关） |
| §4 风险 K4 | 内核/壳更新协议演进不同步 | **风险显著降低**（壳不再解析内核的更新协议） |
| §4 新增 K11 | — | **原地安装无旧版本**：若不备份则无法回滚 → 已列为强制步骤 |

### 修正带来的净收益

1. **冷启动可用**：满足「启动即更新壳」——这是用户的核心诉求。
2. **少一个安全妥协**：不再需要 `dangerousInsecureTransportProtocol`（公网 HTTPS 天然满足 Tauri 的 TLS 强制）。
3. **少一组协议耦合**：壳与内核之间不再有「更新协议」需要同步演进（原 K4 风险基本消失）。
4. **内核职责更纯**：只做它独有的能力——**受监督的安全网**，不重复公网分发的活。

## 九、修正后的「壳更新全流程」（含失败路径）

```
① 壳启动 → 读 identity.json 里上次的 attempt（或自增后写回）
② 只读探针：平台/网络/安装形态
    · 网络不可达 → 记录原因 → 放行（不阻断）
    · installKind=deb → 标记「不可自更新」→ 放行 + 面板提示走 apt
③ 门 0：查公网发布通道（3s 超时）
    · 无更新 → 放行
    · 有更新：
        a. 备份当前产物 → ~/.dsh/shell/cache/<V_old>/（+ 写 journal.from）
        b. 下载 V_new + 验签（失败 → 放行，用 V_old 继续）
        c. 安装（平台机制；失败 → 放行，用 V_old 继续）
        d. app.restart() → 进入 V_new
④ V_new 启动：
    · 写到 shell.log + identity.json（attempt 自增）
    · 走到 finish_boot → POST /shell/health {phase:ready, version:V_new}
⑤ 内核（若在运行）：
    · 收到 ready 且版本 == journal.to → confirmed=true，清 journal
    · 若 journal 未确认且 attempts > 2 → 判坏：
        - pinnedVersions += V_new
        - 用 cache/<V_old>/ 重新安装 V_old（原子）
        - 事件 shell_update_rolled_back + 桌面通知
⑥ 若内核不在运行：
    · 壳自身在门 0 前已备份 → 新版本起不来时无法自动恢复（诚实边界）
    · 缓解：Linux AppImage 可由壳自身换回备份文件；macOS/Windows 依赖内核或用户手动重装
```

## 十、需要你确认的一点

修正后，**「强制更新」的语义是**：

> 壳启动时**尽力**从公网通道更新自己；**失败/离线/达阈值则放行**，用现有版本进入引导。

这与你的「先更新壳，再走引导」一致，唯一区别是不把用户**永久**挡在门外。
若你希望更强制，可选：**达到阈值后不静默放行，而是显示一个「更新失败，重试/继续」的选择页**
（既有强制感，又保留可用性）。这一点请确认。
