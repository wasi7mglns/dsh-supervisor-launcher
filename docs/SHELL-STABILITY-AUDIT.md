# 桌面壳稳定性深度审计（稳定与可靠优先，不做开发）

> 判据（用户定稿）：**以稳定和可靠作为最终判断**，承认"有舍有得"，按工业级标准。
> 本文只做审计与讨论，不含任何代码变更。

---

## 一、结论摘要（先给判断）

**1. 当前壳的根本风险不在"更新"，而在"它是不可自愈的单点"。**

已取证的结构性不对称：

| 组件 | 所有权 | 监督 | 崩溃后 | 日志 |
|---|---|---|---|---|
| 守卫（内核） | 用户级（`~/.local/bin`） | **systemd `Restart=always`, `RestartSec=5`** | 自动恢复 | 落盘（guard.log/events） |
| 桌面壳 | **root（`/usr/bin`, nobody:nogroup）** | **无**（gnome-session 的 `.desktop` 一次性拉起） | **无人恢复** | **无**（仅内存 Vec + stderr） |

即：**内核是自愈的，壳不是**。用户侧"打不开"的投诉，绝大多数会落在壳这一侧，而这一侧既无日志、也无重启、也无法原地更新（root 所有）。

**2. "强制更新壳"这个诉求本身是合理的，但必须以"更新失败绝不阻止启动"为前提。**
强制更新的工业级含义是"**优先且强力地尝试**"，而不是"**无条件阻断启动**"。理由：
老壳 + 老内核是**已验证可用**的组合；把用户拦在门外（=什么都用不了）比让他跑一个旧组合糟得多。

**3. 最高稳定性的方向不是"把更新做得更花"，而是"让壳小到几乎不需要更新"，并给它一条可回滚的更新通道。**

### P2 — 与"更新"直接相关的风险（用户本次关注点）

| # | 风险 | 说明 |
|---|---|---|
| F10 | **原地更新不可能** | 已安装壳在 `/usr/bin`（root 所有）。任何"自我替换"都需提权 → 提权失败/中断 = 不可用 |
| F11 | **更新不可回滚** | 原生二进制被替换后，旧版本已不存在；新版本若起不来，用户无退路 |

| F13 | **更新与运行耦合** | 若让运行中的壳自我下载并替换，任一中途失败（断电/断网/校验失败）都可能留下半成品 |
| F14 | **版本配对无约束** | 壳装内核走 `core_plan` → **总是 latest**，不校验兼容区间 → 旧壳可能装出它不认识的新内核 |

## 四、结构性诊断（为什么壳会脆弱）

**D1. 分发形态与更新需求不匹配。** 壳以**系统包**（`.deb`/`.msi`/`.dmg`）分发到 root 所有的系统目录，
但它的更新需求是**频繁且用户级**的。用系统包通道承载用户级热更新，天然需要提权、不复用用户目录、无法并存多版本 → 更新必然"原地替换、不可回滚"。

**D2. 壳承担了它不该承担的"实时初始化"逻辑。** Node 探测/安装、内核定位/安装、守卫拉起、面板导航全在壳里。
这些逻辑**会随内核协议演进**（例如本次端口架构重构、升级流程修复），于是壳被迫跟着改——**更新压力来自职责错配，而非真的需要新二进制**。

**D3. 壳硬耦合内核内部实现细节。** `env.rs` 直接解析内核的 `config.json` 取 `apiPort`/`closeAction`。
虽然注释称"唯一解析入口"是好的纪律，但它意味着**内核的配置文件格式是壳的公开契约**；该文件一旦演进，壳静默回退（F6）。

**D4. 可观测性为零。** 内核侧我们把大量精力投在日志/事件/任务可观测上（本项目已建立的 guard.log / events / tasks 体系），
而壳侧一行都不落盘。**任何"壳打不开"的问题都无法定位**——这与本次内核升级问题查证困难的成因同源。

**D5. 无自愈、无降级、无逃生舱。** 内核有 `Restart=always`、有 `_crashHalted` 有界停靠、有回滚；壳三样都没有。

## 五、稳定性原则（工业级，按优先级）

**L1 最小职责原则。** 壳只应保留"**不能在别处安全完成**"的事。凡是能下沉到内核/面板（可热更新、可回滚、有日志）的逻辑，都不该留在壳里。
职责每下沉一分，壳的更新压力就少一分——**这是稳定性的第一来源**。

**L2 不可自愈之物不得成为唯一入口。** 既然壳无法被系统级监督，就必须保证"**它坏了也有路走**"（降级路径 / 逃生舱），
而不是依赖它永不坏。

**L3 更新与运行分离。** 运行中的进程**绝不自我替换**。更新由独立方执行（内核已是被监督的一方，最合适），
并以**原子切换 + 并存多版本**落地。

**L4 一切自动化都必须有界、可观测、可回滚。** 尝试计数、放弃阈值、落盘日志、自动回退——四项缺一不可。
（此原则在本项目内核侧已经实践：升级 hold 有超时自愈、崩溃重启有 backoff 上限、升级失败有回滚。）

**L5 失败必须降级，不得阻断。** 更新失败 → 继续用旧版本；配置读不到 → 明说而不是静默猜；面板起不来 → 给诊断面板而不是空白窗口。

**L6 版本配对是原子单元。** 壳与内核应作为**兼容对**一起演进与回退。
"新壳+旧内核"或"旧壳+新内核"都是**未验证组合**，出问题时应回退到**已知可用的配对**，而不是只回退一半。

## 六、有舍有得：必须显式做出的取舍

工业级的要义不是"全都要"，而是**把代价摆到桌面上选定**。

### 取舍 1：更新及时性 ⚖️ 发布风险面

| 选项 | 得 | 舍 |
|---|---|---|
| 壳频繁更新 | 功能最新 | **每次发布都是一个可能砖掉全量用户的窗口**；且需维护签名/安装器矩阵 |
| **壳极少更新（推荐）** | 发布风险面趋近零 | 原生层改进变慢 |

**判断**：选后者。把逻辑下沉，让壳**几乎不需要更新**——这是收益率最高的一步，且几乎无代价（面板本就随内核热更）。

### 取舍 2：原地更新（需 root）⚖️ 并存多版本（用户级）

| 选项 | 得 | 舍 |
|---|---|---|
| 原地替换 `/usr/bin/...` | 干净、单一版本 | **需 root、不可回滚、中断即不可用** |
| **用户级版本目录 + 指针（推荐）** | **无需 root、原子切换、天然回滚、可并存** | 系统包里的壳会长期停留在旧版（它退化为"启动垫片"）；需自建校验与 GC |

**判断**：选后者。系统包里的壳**接受它陈旧**，因为它只是垫片；真正的壳在用户目录里演进。

### 取舍 3：强制更新 ⚖️ 可用性保障

| 选项 | 得 | 舍 |
|---|---|---|
| 无条件强制（不更新不让用） | 版本高度统一 | **一次坏发布 = 全体用户开不了应用** |
| **强制尝试 + 有界失败即放行（推荐）** | 绝大多数用户拿到新版；极端情况仍可用 | 少数用户可能滞留旧版（可用事件上报暴露） |

**判断**：选后者。**"强制"必须让位于"可用"**——这是工业级 updater 的共识（Chrome/VS Code 均如此）。

### 取舍 4：壳的自绘窗口（`decorations:false` + `transparent:true`）⚖️ 渲染健壮性

| 选项 | 得 | 舍 |
|---|---|---|
| 保留自绘/透明 | 视觉统一、沉浸 | **Linux/Wayland 下透明与 GPU 问题高发**（F5），且无降级 |
| **保留外观 + 增加"安全模式"回退（推荐）** | 外观不变，坏环境仍可开 | 需一条降级路径 |

**判断**：外观可以保留，但**必须有"检测到渲染异常即以系统装饰重启"的降级**。

### 取舍 5：是否保留原生壳 ⚖️ 彻底去壳（战略级）

这是最需要用户拍板的一条。

| 选项 | 得 | 舍 |
|---|---|---|
| 保留 Tauri 原生壳 | 托盘、原生窗口、离线首启体验、系统集成 | 三平台构建/签名/安装器矩阵；系统 WebView 依赖；**本审计的 F1–F14 全部存在** |
| **极小托盘助手 + 系统浏览器承载面板** | **几乎消除壳更新需求**（浏览器永远是新的）；消除 WebKit 依赖与签名/打包负担；爆炸半径最小 | 失去原生窗口观感的一致性、深度系统集成、纯离线首启引导体验 |
| 只留"启动脚本 + 浏览器" | 最小 | 无托盘、无单实例管控、退出语义弱 |

**判断**：若"稳定与可靠"是**最终判据**且优先级高于外观一致性，这一条应当被认真评估——
因为面板本来就是内核托管的 Web 页面，**壳对端到端功能并非必需**，它提供的是"容器与便利"。

## 七、推荐稳定形态（若保留原生壳）

### 形态：**冻结垫片 + 用户级 A/B 版本槽 + 健康检查自动回退**

```
[L0] 系统包里的壳（垫片，几乎永不更新；root 所有没关系，因为只读不写）
      │  职责：读指针 → 校验目标版本可用 → exec 之；异常 → 回退自带版本
      │  自带"最后防线"：即使所有热更新版本都坏，它也能起一个旧但可用的壳
      ▼
[L1] 用户级版本槽  ~/.dsh/shell/
      ├── current                 ← 指针（当前应运行的版本）
      ├── previous                ← 上一个已知可用版本（回滚目标）
      ├── versions/<v>/…          ← 并列版本（含 .ok 健康标记）
      ├── bootstrap.json          ← 落盘日志 + 尝试计数 + 版本上报
      └── staged/<v>/             ← 待启用（原子 rename 后就位）
      ▼
[L2] 壳进程（Tauri）：Node → 内核 → 守卫 → 面板
      · 启动即写落盘日志（F4 消除）
      · 达到健康点 → 写 versions/<v>/.ok（供 L0 判定成败）
      · 连续 2 次未达健康点 → L0 自动把 current 回退到 previous
```

### 关键机制（逐条对应上文原则）

| 机制 | 解决 | 原则 |
|---|---|---|
| L0 垫片永不自我替换 | F10/F11/F13 | L3 |
| 用户级版本槽（无需 root、可并存） | F10 | L3 |
| `current` 指针原子切换 + `previous` | F11 | L3/L4 |
| `.ok` 健康标记 + 尝试计数 + 自动回退 | F11/F13 | L4/L5 |
| `bootstrap.json` 落盘日志 + 壳版本上报 | F4/F12 | L4 |
| 更新失败 → 用旧版继续启动 | 强制更新的副作用 | L5 |
| 壳清单声明所需内核区间 | F14 | L6 |
| 配置读不到 → 明确报错而非静默回退 | F6/F7 | L5 |
| 自绘窗口渲染异常 → 安全模式 | F5 | L5 |
| panic 收敛为"捕获+落盘+降级" | F1/F2 | L5 |

### 谁执行更新（关键设计选择）

两种都可行，但**推荐由内核（守卫）执行**：

| 执行方 | 优点 | 缺点 |
|---|---|---|
| 壳自己 | 首启即可更新 | 需在壳里保留网络+校验+版本比对逻辑 → **与 L1 最小职责冲突**；且运行中自我更新的风险面大 |
| **内核（守卫）** | 它已被 systemd 监督、已有网络/镜像/校验/日志/任务体系 | 需守卫已在运行（首次安装后的首次更新即可享受） |

**判断**：由内核**预置**（下载+校验+落盘到 `staged/` 并更新 `current`），壳在**下次启动**时自然生效。
这样壳里**不需要任何更新逻辑**——完美符合 L1，且"更新"与"运行"彻底分离（L3）。

代价：壳更新**不在首启即时发生**，而是"下次启动"生效。**这个代价应当接受**——换来的是壳内零更新代码。

## 八、与用户原始诉求的对齐（启动时序）

原始诉求：启动时同时检测壳与内核；壳有新版本 → 先强制更新壳 → 重启壳 → 再检测内核 → 更新内核。

**审计意见：时序方向正确，但"强制"的语义必须修正。**

```
L0 垫片
  ├─[门 0] 壳版本（读 current vs 最新）
  │    ├─ 已最新 / 无更新 / 离线 / 尝试已达阈值 → 放行（并落盘记录原因）
  │    └─ 有更新 → 切换到新版本槽 → 启动新壳
  │            新壳达健康点 → 确认；未达 → 回退 previous → 用旧版继续
  ├─[门 1] Node 运行时
  ├─[门 2] 内核（现有 core_plan → core_apply）
  └─[门 3] 守卫 → 面板
```

**为什么方向正确**：新壳才可能知道新内核的安装要求（新的包名/镜像/前置条件）。
**为什么必须修正"强制"**：见取舍 3——无条件阻断会把"更新故障"升级为"完全不可用"，反而**降低**可靠性。

**另需对齐的一点**：若采用"内核预设、下次启动生效"的执行方选择，则门 0 的语义是"**应用已预设的更新**"
（而非当场下载）。这既满足用户"先壳后内核"的时序，又让壳内零更新逻辑。

## 九、待用户拍板的决策点

| # | 决策 | 选项 | 我的建议 |
|---|---|---|---|
| D1 | **是否保留 Tauri 原生壳** | 保留 / 去壳（浏览器承载面板 + 极小托盘助手） | 先明确功能必要性；若外观一致性非硬需求，去壳是稳定性最优解 |
| D2 | **更新执行方** | 壳自己 / 内核预设、下次启动生效 | **内核预设**（壳内零更新逻辑） |
| D3 | **系统包里的壳是否接受长期陈旧** | 接受（作为垫片）/ 不接受（则必须保留提权原地更新，风险高） | **接受** |
| D4 | **"强制"的边界** | 无条件阻断 / 有界尝试后放行 | **有界尝试后放行** |
| D5 | **自绘透明窗口是否保留** | 保留 / 改为系统装饰 / 保留+安全模式回退 | **保留 + 安全模式回退** |
| D6 | **优先修复项（无论选哪条路线）** | 见下 | **F3/F4/F6/F12 四条** |

### 无论最终选哪条路线，都建议先做的四件事（纯稳定性、零路线依赖）

1. **F4 壳落盘日志** —— 没有它，后续任何壳问题都无法定位。这是所有决策的前提。
2. **F3 壳自愈** —— 壳崩溃后至少有路可走（用户级自启守护 / 或托盘子进程看护）。
3. **F12 壳版本可见** —— 壳把 `{version, platform}` 报给内核，面板可见。
4. **F6/F7 配置读取健壮化** —— 读不到就**明确告知**，不静默回退到错误端口；统一兜底默认值。

这四项**不改架构、不引入新风险**，却能把"不可诊断"变成"可诊断"，是所有后续工作的地基。
