# 桌面壳：原生形态定案后的稳定架构（讨论稿，不做开发）

> **D1 已定案（用户）**：必须保留 Tauri 原生壳——「不然就不是一个桌面级产品了」。
> 最终发布形态 = **桌面级产品**。本文在此前提下重新推演稳定与更新架构。
> 判据不变：**稳定与可靠优先**，承认有舍有得，工业级标准。

---

## 一、D1 定案带来什么变化

**不变的**：壳仍要解决「原生二进制如何可靠更新」。

**改变的（重要）**：既然壳是产品的**长期门面**，那么

1. 它**必须**具备桌面级产品的可靠性工程——而当前 **F1–F5（panic / 无自愈 / 零日志 / 无降级）**
   在这个定位下从「改进项」升级为「发布阻塞项」。
2. 它**必须**被签名与公证——否则 macOS Gatekeeper / Windows SmartScreen 会让
   「桌面级产品」变成「装不上的产品」。
3. 它**必须**有可演进的更新通道——否则每次壳更新都是一次高风险裸奔。

**推翻的**：上一份审计中「去壳（浏览器承载面板）」的选项，正式作废。
随之，**「让壳小到不需要更新」从「可选策略」变成「必须落实的头号纪律」**——
因为无法去壳，就只能尽量让这个无法回避的原生二进制**少变、变时可靠**。

## 二、工业先例（已核实事实，非推断）

| 产品 | 安装形态 | 更新通道 | 关键事实 |
|---|---|---|---|
| **VS Code（Linux deb）** | .deb | **apt 源，由系统包管理器更新** | 官方文档原文：.deb 会提示安装 apt repository 与 signing key，
「enables auto-update through the system package manager」。**应用自身不自我替换** |
| **VS Code（通用）** | tar.gz / AppImage | 应用内自更新 | 并提供 UpdateMode 策略（default / start / manual / none）供企业集中管控 |
| **Chrome / Discord / Slack** | 系统包 + 发行商源 | 系统包管理器 / 独立更新器 | **更新器与应用分离**（Google Update / Keystone 等），从不在应用内替换自己 |
| **Tauri updater（官方）** | — | 应用内自更新插件 | **强制签名**（minisign，不可关闭）；**Linux 仅 AppImage 是更新产物**；**无回滚机制** |
| **Tauri NSIS 安装器** | Windows | — | 官方文档原文：**默认即为「仅当前用户」安装**（装到 %LOCALAPPDATA%，**无需管理员权限**）；
设为 perMachine 才需要管理员 |

### 三条可复用的工业共识

**共识 1：Linux 上的「系统包」与「应用内自更新」是互斥的。**
这不是我们的特殊情况，而是行业既定事实（VS Code 用 apt 源解决，Chrome 用自有 apt 源解决）。
硬要在 .deb 上做自替换，等于和 dpkg 的数据库打架 → **必然不稳定**。

**共识 2：桌面产品的更新，普遍采用「per-user 安装」来规避提权。**
已核实的 Tauri 官方默认行为正好支持这一点，且与「应用内自更新」天然兼容。

**共识 3：更新必须「原子 + 可回滚 + 有健康确认」。**
Chrome / VS Code 都会保留上一版本，并在新版启动失败时回退。
**Tauri updater 不提供回滚**，这一层必须自建。

## 三、三平台的正确答案（不同平台答案不同，这是规范而非妥协）

| 平台 | 建议安装形态 | 更新通道 | 需要提权 | 能否应用内强制更新 |
|---|---|---|---|---|
| **Windows** | NSIS per-user（%LOCALAPPDATA%，Tauri 默认） | Tauri updater（-setup.exe 替换） | **否** | **能** |
| **macOS** | .app（由 dmg 装载；可落 /Applications 或 ~/Applications） | Tauri updater（.app.tar.gz） | 通常否 | **能** |
| **Linux（主通道）** | **AppImage**（用户级） | Tauri updater（AppImage 替换） | **否** | **能** |
| **Linux（可选通道）** | .deb | **apt 源 → 系统包管理器** | 是（apt） | **不能（设计使然）** |

**结论**：想要「桌面级 + 应用内强制更新」，Linux 就**必须把 AppImage 作为自更新的主通道**，
.deb 作为可选的系统集成通道（由 OS 更新，应用内只做**提示**）。
这与 VS Code 完全一致的工业解法，不是降级方案。

## 四、核心架构建议：**内核（受监督方）负责修复壳（不受监督方）**

这是本方案最关键的洞察，也是当前架构「天然欠拟合」的补救点。

### 4.1 事实不对称

| | 所有权 | 监督 | 崩溃 | 日志 |
|---|---|---|---|---|
| 内核 / 守卫 | 用户级 | **systemd Restart=always** | 自动恢复 | 有 |
| 桌面壳 | 系统级（root） | **无** | **无人恢复** | **无** |

### 4.2 推论：让「能自愈的一方」看护「不能自愈的一方」

壳坏掉时（起不来、无日志、被更新到坏版本），**内核很可能仍然活着**（它是独立 systemd 服务）。
因此**内核有能力修复壳**——这是现成的、已被监督的执行者，**无需新增任何守护进程**。

```
┌─ 内核（受 systemd 监督，有日志/事件/任务/网络/镜像体系）──────────┐
│  · 预置壳更新：下载 → 验签 → 落盘到 versions/<v>/                 │
│  · 记录「期望壳版本」与更新日志（写独立 json，非 state 投影）      │
│  · 观察：壳是否在预期时间内上报「我已健康启动」                    │
│  · 超时 / 连续失败 → **自动回退到上一个已知可用版本** + 事件 + 通知 │
└──────────────────────────────────────────────────────────────────┘
         │ 读取指针 / 上报健康
┌────────▼─────────────────────────────────────────────────────────┐
│ 壳（Tauri 原生，保留）                                            │
│  · 启动即写**落盘日志**（消除 F4）                                 │
│  · 走完 Node → 内核 → 守卫 → 面板 → 调 finish_boot = **健康确认**  │
│  · 自身**不含任何更新/版本比对逻辑**（职责最小化，符合 L1）        │
└──────────────────────────────────────────────────────────────────┘
```

**收益**：
- 壳内**零更新逻辑** → 壳几乎不再因更新机制而改动（直接降低更新频次）。
- 即使壳**完全起不来**（连日志都没有），内核仍能回退它 → 破解「壳坏了没人修」的死局。
- 复用内核已有的网络/镜像/校验/日志/任务/事件全套工程，**不新增基础设施**。

**代价**：壳更新不在「首启瞬间」完成，而是**内核预设 → 壳下次启动生效**。
这个代价应当接受（见取舍 B）；作为补偿，可在面板提供「立即重启壳以应用更新」。

## 五、稳定形态（推荐）

### 形态定义：**原生壳（标准安装）+ 版本槽 + 健康确认 + 内核回退**

```
[L0] 原生壳（系统/用户级标准安装，Tauri）——桌面形态与 OS 集成由此保证
      │  启动先读「当前应运行版本」指针；指针不可用/目标损坏 → 用自带版本（最后防线）
      ▼
[L1] ~/.dsh/shell/
      ├── current             ← 指针（内核写入）
      ├── previous            ← 上一个已知可用（回退目标）
      ├── versions/<v>/       ← 并列版本（含 .ok 健康标记）
      ├── update-journal.json ← from / to / startedAt / attempts / confirmed
      └── shell.log           ← 壳落盘日志（含启动各阶段与失败原因）
      ▼
[L2] 壳进程：Node → 内核 → 守卫 → 面板 → finish_boot（= 健康确认）
```

### 更新全流程（含失败路径）

1. 内核检测到新壳版本 → 下载 → **验签** → 解包到 versions/<v>/（临时目录 → 原子 rename）
2. 写 update-journal（from=X, to=Y, attempts=1, confirmed=false）；同时把 X 备份为 previous
3. 写 current=Y（**原子替换**）；面板提示「重启以应用更新」
4. 壳启动 → 写落盘日志 → 走引导 → 达 finish_boot → 向内核确认
   → 内核清空 journal 并给 Y 打 .ok
5. **失败路径**：内核发现 journal 未确认且超时 / 启动次数达阈值（如 2 次）
   → current=previous（原子回退）→ 事件 + 桌面通知 → 壳以已知可用版本启动
6. 全程每一步都写事件日志（可审计、可回放）

### 为什么「健康确认」是这套设计的枢纽

没有健康确认的更新 = 只看「装上了」，不看「能不能用」。
本项目**恰好已有**这个钩子：引导页的 finish_boot 是「环境全就绪」的精确标志。
把它升级为「更新确认信号」，就得到与 Chrome / VS Code 同级的更新可靠性，而**几乎零新增代码**。

## 六、「强制更新」的正确语义（再次明确）

用户原始诉求：**壳有新版本 → 先强制更新壳 → 重启壳 → 再检测内核 → 更新内核**。

**时序方向：完全正确，予以确认。**
理由：新壳才可能知道新内核的安装要求（新包名 / 新镜像 / 新前置条件）。
反过来（先内核后壳）就是此前「升级恒失败」那类问题的同源变体。

**「强制」的语义：必须修正为「强力尝试 + 有界失败即放行」。**

| 语义 | 后果 |
|---|---|
| 无条件强制（不更新不让用） | **一次坏发布 = 全体用户开不了应用**；且离线用户直接不可用 |
| **强力尝试 + 有界失败放行**（推荐） | 绝大多数用户拿到新版；极端情况退到「旧壳 + 旧内核」这个**已知可用组合** |

**这不是妥协，而是工业级共识**：Chrome / VS Code 的自动更新同样遵守「失败就继续用旧版」。
把用户拦在门外，是把「更新故障」升级成「完全不可用」，**净降低**可靠性。

### 最终启动时序

```
壳启动
  ├─[门 0] 应用壳更新（内核已预设）
  │    ├─ 无更新 / 离线 / 已达阈值 / 指针不可用 → 放行（落盘记录原因）
  │    └─ 有更新 → 切到新版本槽 → 启动新壳
  │              达 finish_boot → 确认；未达 → 内核回退 previous → 旧版继续
  ├─[门 1] Node 运行时（现 env.rs）
  ├─[门 2] 内核（现 core_plan → core_apply）——且须校验**兼容区间**（见 §7）
  └─[门 3] 守卫 → 面板
```

## 七、版本配对（新增要求）

**问题（现状 F14）**：壳装内核走 core_plan → **总是 latest**，不校验兼容区间 →
旧壳可能装出它不认识的新内核；一旦内核协议演进（如本次端口架构重构），旧壳可能无法正确拉起。

**建议**：把「壳 + 内核」视为**兼容对**，而非两个独立组件。
- 壳清单 / 发布元数据声明它**要求的内核区间**（如 kernelMin / kernelRecommended）。
- 内核侧也声明它的**最低壳版本**。
- 不匹配时：优先「把壳升到兼容版本」，而非「把内核降到旧版」。
- 回退时**整对回退**到已知可用组合（回退一半是未验证状态）。

## 八、必须补齐的桌面级可靠性工程（因保留原生壳而成为阻塞项）

| # | 事项 | 现状 | 为什么是阻塞项 |
|---|---|---|---|
| R1 | **壳落盘日志**（滚动、含启动各阶段） | 无（全在内存） | 没有它，任何「打不开」都无法定位；桌面产品不可接受 |
| R2 | **壳崩溃自愈**（内核看护 / 用户级自启守护） | 无 | 桌面产品不能「死了就死了」 |
| R3 | **panic 收敛**（.expect / lock().unwrap()） | 9 处 | 桌面产品不能因缺个图标就静默死掉 |
| R4 | **壳版本可观测**（上报内核 → 面板可见） | 无 | 否则「壳是否更新成功」无法判断 |
| R5 | **配置读取健壮化**（不静默回退到错端口） | 兜底值还不一致（3100 vs 36360） | 静默猜错端口 = 长时间卡住且无提示 |
| R6 | **渲染降级（安全模式）** | 无 | Linux / Wayland 透明窗口与 GPU 问题高发，桌面产品需有退路 |
| R7 | **签名与公证** | 无 | macOS 不签名不公证 → Gatekeeper 拦截；Windows → SmartScreen 告警。**桌面级产品的硬性前提** |

## 九、有舍有得（因保留原生壳而新增的取舍）

### 取舍 A：Linux 自更新能力 ⚖️ 系统包集成度

| 选项 | 得 | 舍 |
|---|---|---|
| **AppImage 为主通道** | 应用内自更新可用、无需提权 | 桌面集成弱（需自行安装 .desktop / 图标）；现有 .deb 用户不在自更新覆盖内 |
| deb 为主通道 + apt 源 | 与系统集成最好、apt 自动更新（VS Code 同款） | **应用内「强制更新」不可能**；需维护 apt 源与签名 key |
| 两者都发 | 覆盖最广 | 需明确「哪条通道能自更新」，deb 用户要靠 apt（需文档与 UI 提示） |

**建议**：两者都发，但**明确分工**——AppImage = 自更新通道；deb = 系统集成通道（apt 更新 + 应用内提示）。

### 取舍 B：更新执行方 ⚖️ 更新时效

| 选项 | 得 | 舍 |
|---|---|---|
| 壳自己更新 | 首启即时生效 | 壳内保留网络/校验/回滚逻辑 → **与「壳最小职责」冲突**；运行中自替换风险高 |
| **内核预设、下次启动生效（推荐）** | 壳内**零更新逻辑**；受监督方修复不受监督方 | 非即时；需面板提供「立即重启以应用」 |

### 取舍 C：签名成本 ⚖️ 分发可信度

桌面级产品的硬性支出（**必须纳入预算**）：
- **macOS**：Apple Developer Program（约 99 美元/年）+ 公证流程。**不签名 + 不公证 = 用户装不上 / 被拦**。
- **Windows**：代码签名证书（OV / EV，约数百美元/年；亦有订阅式云签名服务）。**无签名 = SmartScreen 告警**，且更新体验受损。
- **Linux**：AppImage 本身无需系统级签名；但 Tauri updater 的更新产物**强制 minisign 签名**
  （密钥须异地备份——**丢失则该批用户永久失去更新能力**）。

> 这是「保留原生壳 + 桌面级产品」定位带来的**必然成本**，不是可选项。

### 取舍 D：更新时效性 ⚖️ 发布风险面（原取舍 1，仍然成立）
**建议维持「壳极少更新」纪律**：凡能下沉到内核 / 面板 / 引导页 JS 的逻辑，绝不写进 Rust 二进制。

## 十一、无论 D2–D6 如何选，建议先做的四件事（零架构风险）

1. **R1 壳落盘日志** —— 所有后续决策的前提：没有日志，连「坏在哪」都不知道。
2. **R4 壳版本上报** —— 让「壳是否更新成功」从此可判断。
3. **R2 / R3 自愈与 panic 收敛** —— 让壳不再「一坏就永久坏」。
4. **R5 配置读取健壮化** —— 读不到就**明确报错**，不静默回退到错误端口；统一兜底值。

这四项**不引入更新机制、不改分发形态、无新基础设施依赖**，
却把壳从「不可诊断、不可自愈」拉升到「可诊断、可自愈」。
**它们是任何更新方案的地基**——在讨论「怎么更新」之前，先让壳「能被看懂」。
