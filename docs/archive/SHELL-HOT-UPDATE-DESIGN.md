# 桌面壳热更新设计方案（Shell Hot-Update）

> 目标（用户要求）：启动时**同时**检测桌面壳与内核版本；**壳有新版本 → 先强制更新壳 → 重启壳 → 再检测内核 → 更新内核**。
> 本文给出可落地路线、各路线硬约束、以及**必须配套的安全护栏**（否则"强制更新"会把用户搞成砖）。

---

## 0. 现状（已取证）

| 项 | 事实 |
|---|---|
| 壳形态 | Tauri 2 + Rust（`dsh-supervisor-gui` v0.1.0），frontendDist=`bootstrap/` |
| 壳产物 | `.deb` / `.AppImage` / `.dmg` / `.msi`（壳仓 CI：`tauri build` + `action-gh-release`） |
| 壳自更新 | **完全没有**（无 `tauri-plugin-updater`，无版本自检） |
| 壳职责 | 极薄：确保 Node → 定位内核 → 拉起守卫 daemon → 打开面板（`bootstrap.html` 驱动 `core_plan → core_apply → guard_start → guard_ready → finish_boot`） |
| 壳版本可见性 | **内核/面板完全不知道壳版本**（壳未落盘自身版本，内核无相关字段） |
| 内核更新 | 已可用：`core.rs` 走 npm（多镜像回退 + 显式 `--prefix`） |
| 面板 UI | 来自**内核**的 `ui-react`（守卫托管）——**本身已随内核热更新** |
| 壳版本 vs 内核版本 | 两条独立版本线（壳 0.1.0 / 内核 0.1.2-BETA.7），无耦合声明 |

**关键认识**：壳是薄引导器，用户可见的一切（面板）已经随内核热更。壳需要更新的场合**只有原生/Rust 层变化**
（Node 安装逻辑、新的引导步骤、托盘/窗口行为）。因此壳热更新的**真实频次很低**，但一旦需要就必须可靠。

## 1. 目标启动时序（有序门）

```
壳进程启动
  │
  ├─[门 0] 壳自更新（强制）        ← 新增
  │    ├─ 读引导状态（上次尝试记录）
  │    ├─ 检查壳最新版本（发布清单）
  │    ├─ 无更新 / 已达放弃阈值 / 离线 → 放行到门 1
  │    └─ 有更新 → 显示进度 → 下载+校验+安装 → 重启壳
  │                 （重启后回到门 0：版本已匹配 → 放行）
  │
  ├─[门 1] Node 运行时（现有 env.rs）
  ├─[门 2] 内核版本（现有 core_plan → core_apply，npm）
  └─[门 3] 拉起守卫 → 打开面板
```

**为什么壳必须排在前面**：新壳才可能知道新内核的安装要求（新的包名/镜像/前置条件）。
反过来（先内核后壳）会让旧壳用自己的旧规则去装新内核 → 正是此前「升级恒失败」那一类问题的同源变体。

---

## 2. 三条可选路线

### 路线 A：Tauri 官方 updater（`tauri-plugin-updater`）

官方文档已核实（v2.tauri.app/plugin/updater）：

- 平台：Linux ✓ / Windows ✓ / macOS ✓（**不支持** Android/iOS）
- **强制签名，不可关闭**：需 minisign 密钥对——公钥进 `tauri.conf.json`，私钥进 CI secret
- 需 `bundle.createUpdaterArtifacts: true`；Rust API：`app.updater()?.check()` → `download_and_install()` → `app.restart()`
- 静态清单 `latest.json` 可直接放 GitHub Releases：
  `https://github.com/<owner>/<repo>/releases/latest/download/latest.json`
- 更新产物（v2 模式，**与安装包不同**）：
  - Linux：`应用.AppImage` + `.sig`
  - macOS：`应用.app.tar.gz` + `.sig`
  - Windows：`应用-setup.exe` + `.sig`（NSIS）/ `应用.msi` + `.sig`

**优点**：官方维护、签名校验内建、三平台安装语义已处理、`app.restart()` 现成。

**硬约束（决定它是否适合本项目）**：

| # | 约束 | 影响 |
|---|---|---|
| A1 | **Linux 只有 AppImage 是更新产物**；`.deb` 安装的副本**无法自更新**（改系统包需 root/dpkg） | 本项目同时发 `.deb` + `.AppImage` → **deb 用户被排除在自更新之外** |
| A2 | macOS 更新产物是 `.app.tar.gz`，不是 `.dmg`；需 CI 额外产出 | 壳仓 CI 需改造（当前只传 dmg） |
| A3 | Windows 建议 NSIS 才能静默安装（当前只 build `msi`，MSI 更新会弹交互） | 壳仓需加 nsis target |
| A4 | **私钥一旦丢失，已安装用户永远无法再更新** | 密钥必须异地备份，属长期运营风险 |
| A5 | 更新失败**无回滚**；新版本若起不来，用户直接不可用 | **必须配循环护栏与逃生舱**（见 §3） |

### 路线 B：自管理版本目录 + exec 最新版（"引导器 + 热插拔"）

思路：壳不"安装"新版本，而是像浏览器更新器那样维护**并列版本目录**：

```
~/.dsh/shell/
  ├── current                      ← 指针文件（记录当前应运行的版本）
  ├── versions/
  │     ├── 0.1.0/  (完整可执行 + 资源)
  │     ├── 0.2.0/
  │     └── 0.2.1/
  └── bootstrap-state.json         ← 尝试计数 / 上次目标版本 / 已装版本
```

启动流程：壳（已安装的那个）读发布的 shell 清单 → 若有新版则下载到 `versions/<v>/`（临时目录→校验→原子改名）
→ 更新 `current` → **`exec` 新版本进程并让旧进程退出**（不是 Tauri 的 restart，而是真正的进程替换）。

**优点**：
- **三平台 + 所有安装形态一致**（deb/AppImage/dmg/msi 用户都能覆盖——因为**不碰已安装的包**，只在用户目录放新版本）
- **无需 root**（用户可写目录）
- **回滚天然**：保留 N-1 个版本，改 `current` 即可回退到已知可用版本
- 不依赖 minisign 基础设施（可用 HTTPS + 清单内 SHA-256 校验，或仍做签名校验）
- 子进程 exec 语义清晰，不存在"安装器装到一半失败"的中间态

**代价 / 需自建**：
- 完整性校验要自己做（SHA-256 + HTTPS；若要抗篡改则仍需签名）
- 多版本磁盘占用与管理（GC 策略：保留当前 + 上一个）
- macOS 需处理下载文件的 `com.apple.quarantine`，且新 bundle 仍需签名否则 Gatekeeper 拦截
- Windows 上从用户目录 exec 下载来的 exe，可能触发 SmartScreen/杀软告警（需签名缓解）
- 磁盘上"已安装的壳"会长期停留在旧版本（它只是 stub，负责 exec 最新版）——设计上要接受这点

### 路线 C：壳保持极薄，逻辑全部下沉（成本最低）

把可变的引导逻辑从 Rust 二进制里挪出去，shell 只保留"确保 Node + 确保内核 + 开面板"的最小能力。
具体：引导页 `bootstrap.html` 已经是 HTML/JS——可改为**由内核/npm 下发**，于是引导逻辑也能随内核热更，
壳二进制几乎不再需要变化。

**优点**：零新基础设施；与现有 npm 分发链（含国内镜像回退）复用。
**局限**：**原生/Rust 能力的变化无法热更**（这正是"壳热更新"的原始诉求）——它只能减少壳更新频次，不能替代。

## 3. 推荐组合

**C（默认策略）+ B（更新机制）**，A 作为备选：

1. **默认策略 C**：能放进内核/面板/引导页 JS 的逻辑，绝不放进 Rust 二进制 → 壳本身很少需要更新。
2. **更新机制选 B**：因为项目同时分发 `.deb` 与 `.AppImage`（甚至未来 rpm），**A 无法覆盖 deb 用户**；
   B 用一个机制统一覆盖全部安装形态，且**回滚免费**——这点对"强制更新"至关重要。
3. **若倾向标准做法选 A**：需接受 A1–A5 的全部约束，尤其必须**决定 deb 用户怎么办**：
   (a) 只把 AppImage 作为自更新渠道，deb 用户提示手动下载；或 (b) 停发 deb；或 (c) 双轨（deb 用户走 B）。

> 无论选 A 还是 B，**§3 的安全护栏都不可省**——强制更新 + 无护栏 = 一次坏发布就让所有用户开不了应用。

## 4. 安全护栏（强制更新的必要条件）

### G1 循环护栏（最重要）

症状：更新成功但版本比对仍认为"需要更新" → 每次启动都更新+重启 → **无限重启，应用不可用**。
可能来源：清单未及时更新、安装未真正替换、版本号解析差异。

对策（持久化 `bootstrap-state.json`）：
- 记录 `{ targetVersion, attempts, lastAttemptAt }`
- 启动时：若**运行版本 == targetVersion** → 清空记录，放行
- 若 `attempts >= 2` → **放弃强制**，写事件日志，用当前版本继续启动（面板提示"壳更新失败，请手动下载"）
- 否则 `attempts += 1` 后执行更新

> 这与本次已修复的内核升级问题**同源**：任何"自动重试"都必须有界且可观测。

### G2 离线 / 检测失败 ≠ 强制
只有"确实存在新版本且下载+校验成功"才强制。网络失败/清单不可达 → **静默放行**，绝不让用户因断网开不了应用。

### G3 逃生舱
- 环境变量 `DSH_NO_SHELL_UPDATE=1` 跳过本次（用于排障与技术支持）
- 达到 G1 阈值后自动跳过（不依赖用户操作）

### G4 完整性校验
- 路线 A：Tauri 强制签名，**绝不可关闭**；私钥异地备份（丢失=该批用户永久失去更新能力）
- 路线 B：清单内 SHA-256 + HTTPS；若资源允许，同样做签名校验（可用 minisign，不必是 Tauri 的那套）

### G5 回滚可用性
- 路线 B：保留上一个可用版本，`current` 指针可回退；连续失败 2 次自动回退到上一个已知可用版本
- 路线 A：无内建回滚 → 至少保留旧安装包，并给出"重装旧版"的手动路径

### G6 壳版本可观测（当前缺失，必须补）
内核/面板现在**不知道壳版本**。需让壳启动时把 `{ version, platform, arch, updatedAt }` 落到约定位置
（如 `~/.dsh/supervisor/bootstrap.json`），内核读取后在面板展示"桌面壳 x.y.z"。
否则一旦出现"壳没更新成功"类问题，面板上完全看不出来——这正是本次内核升级问题查证困难的同类原因。

### G7 版本耦合声明
壳清单应声明它要求的**内核版本范围**（如 `kernelMin` / `kernelRecommended`）。
新壳落地后按此驱动门 2，而不是各自独立猜测——否则会出现"新壳装了旧内核，功能不匹配"。

## 5. 落地清单（选定路线后）

| # | 事项 | 路线 A | 路线 B |
|---|---|:--:|:--:|
| 1 | 壳落盘自身版本 + 内核读取展示（G6） | 必做 | 必做 |
| 2 | 引导状态文件 + 循环护栏 + 逃生舱（G1/G3） | 必做 | 必做 |
| 3 | 门 0 前置到 `bootstrap.html`/Rust setup，排在 Node/内核门之前 | 必做 | 必做 |
| 4 | 壳仓 CI 产出更新产物 | `.AppImage.sig`/`.app.tar.gz.sig`/NSIS 或 msi | 打包版本目录 tarball + 清单(SHA-256) |
| 5 | 发布清单 | `latest.json`（tauri-action 可自动生成） | 自建 `shell-manifest.json` |
| 6 | 密钥 | 生成 minisign 密钥对，私钥入 CI secret + 异地备份 | 可选（否则仅 SHA-256） |
| 7 | 守卫/面板：展示壳版本 + "检查壳更新"入口 | 可选 | 可选 |
| 8 | 决定 Linux `.deb` 用户策略（A1） | **必须** | 不适用（天然覆盖） |
